# 第一步：解析

目标：先理解需求文档中的产品功能、品牌与交付目标，再提出有依据、可画出来的小巧思，和用户收敛出 2–3 个核心关键词及初步构形方向。下面五项是解析与对话框架，不是必须逐题作答的固定问卷；候选内容随项目生成。

## 输入分支与默认值

- 有上传文档或文档链接：先读正文，记录链接/文件与来源章节，提炼产品核心功能、品牌名、调性和交付要求。读不到时说明障碍，请用户提供可访问正文或口述需求，不猜测文档内容。
- 没有文档且需求不足：先问产品或品牌名字、核心功能或主要解决的问题。允许自然语言回答，不强制补文档；已有答案直接摘要，不重复询问。
- 交付内容先从需求提取。完全未指定时，以 iOS App 图标作为工作默认，不再问使用位置；明确记录默认而非已确认平台。系统版本与导出技术细节留到交付阶段处理。
- 文档宿主、第三方集成功能、参考 UI 不代表本品牌身份，不自动继承它们的品牌色。用户明确排除的颜色记为设计约束。

## 从需求提炼可视化机会

整理一句话产品定义、核心功能与辅助功能、关键交互、产品原则和品牌名。区分“文档明确 / 根据文档推导 / 待确认”，附来源章节；文档报告的验证状态不等于 Agent 独立测试。用户人群未明确时可以记录未知，不额外阻塞构形讨论。

从产品特有的物件、动作、结构关系、反馈、名字含义和字形中寻找视觉机会。例如：用最有辨识度的局部代替整个物件；用轮廓、负形或部件排列表达功能；把交互反馈转成表情；让字母结构与产品符号共用一条边或一个空间。按需求选择适合的手法，不把这些变成每次必选的类别。

每个提出的创意写清“需求依据 → 可画的形态/变化 → 想传达的感受”。优先一眼识别产品、再发现一处巧思；单个方向通常围绕一个主要巧思展开，避免把功能、名字、首字母、表情全部堆在一起。抽象收益如“效率、灵感”需要转成具体视觉动作或形态，不能只换形容词。

## 三个问题方向与两个补充视角

1. **核心功能**：先概括产品最重要的用途，再从文档生成几种不同的视觉表达供选。区分“真实功能”与“怎样画出来”：既可表达整体，也可聚焦标志性部件、动作或反馈。不要只列同义功能词让用户猜最终画法。
2. **品牌名字**：提取或询问准确拼写、大小写与已有含义，再提出可画的名字联想。用户未解释名字时，将语义联想标为设计推导，不编造品牌故事。名字未定可暂用产品描述继续，命名并非默认附加任务。
3. **感受与风格**：从品牌调性提出适合本项目的感受与可执行视觉处理，例如以形状、线条、材质或色彩关系解释如何体现某种感受。已有偏好就复用，未知可先看案例。读取 `icon-styles.md` 作为可用技法参考而非固定选项菜单；最终风格结合真实参考图确认。涉及“当前流行”时核验来源，不用下载排名替代风格热度证据。
4. **需要交付哪些内容**：先列出文档已明确的范围，仅对缺失部分给出适合本项目的建议，例如独立标志、App 图标、字标、配色变体、可编辑母版、设备 mock 或导出资产；不自动全选。区分最终交付和过程中的探索板，避免把所有探索方向都承诺为成品。
5. **根据名字首字母延展**：根据实际名字的首字母、缩写或字形，提出能与功能自然结合的构形机会，说明具体结合点。可以探索单字母、字母负形或字母与物件共形，也保留不使用字母的方向。名字不适合首字母表达、中文名无既定英文写法、或用户不喜欢字母标时，记录不采用/待定，不擅自发明英文名或强行拼字。

面向用户先给简短需求摘要，把问题组织为核心功能、品牌名字、感受与风格三个方向，首字母与交付内容作为适用补充，最多 1–3 轮。再只问缺失信息或有价值的偏好选择。每组候选的数量和措辞由需求决定，通常少量清晰选项即可；不为了凑满五题重复提问。允许自由补充、组合、暂缓或委托 Agent 判断。五项不是五套 Logo，也不是把所有选择塞进一张图。

### 示例：方法可复用，题材不固定

若需求是带情绪表达的键盘产品，可提出：一个可辨认的按键代表输入；以少量键位/负形呈现键盘；让键盘或按键本身带表情；若品牌首字母适合，再探索它与按键轮廓共形。这些是根据功能产生的构形假设，不是今后所有项目的默认选项。

换成旅行记录产品时，应重新从路线、目的地、记录动作或名字字形推导，例如让路线转折形成字母，而不是沿用按键和笑脸。若功能未涉及情绪或人格，也不为了“小巧思”例行增加表情。

## 状态与产出

保存 brief.json 与解析.md：source facts、来源链接/章节、brand_name、product_purpose、keyword_candidates、core_keywords、style_preference、deliverables、initial_letter_directions、creative_opportunities、hard_constraints 与 keyword_confirmation_status。这些是解析阶段可扩展的项目字段，按实际需要补充，无须更改已有项目的基础 schema。

每个 creative_opportunity 记录依据、形态手法、预期感受和 proposed/selected/rejected 状态。交付建议和首字母方向也区分“文档已明确 / 待选择 / 用户确认或委托”，未回复不能写成已确认。最终收敛的 2–3 个关键词负责引导构形；交付清单、风格和首字母是否采用分别保存，不凑成关键词。

用户仅要求解析时，到需求摘要、创意提案与必要问题为止，不提前生成图像或编辑 Figma。完整设计任务按 workflow-1.0.md 的选择/暂选机制继续：进入 `reference-board.md` 的同品类调研与选图，再将创意假设用于 `modular-design.md` 的 6–12 个不同方向探索、2–3 个方向收敛和每个入选意象约 25 个几何变体。初步想法不是最终风格锁定；仅做现有方案小改动时复用已选方向。

客户选择保留在项目内；只把通用流程沉淀到 skill。
