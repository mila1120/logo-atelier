# Logo Atelier 1.0 — 发散、选择与迭代

Agent 与 Figma 协作生成可编辑 SVG，让设计师负责收敛与最终决策。完整项目沿以下 11 步推进；局部请求直接进入对应步骤，复用当前画布和已有选择。

## 交互节奏

- 通常有 **6 个主要设计决策点**：意象 → 参考 → 初稿 → 几何 → 色材组合 → 定稿。需求澄清最多 1–3 轮；终选按实际反馈增加轮次，不承诺固定对话总数，也不为凑轮次强制经历所有终选版本。
- 每轮先由 Agent 根据上一轮结论可靠发散，画出实际候选，再让用户选择。一次问题集中处理一组相关决策；优先用可用的 Codex 选择题工具，附编号、短名称和 Figma 链接，支持多选或自由输入。不要让用户逐张回答 25 个问题。
- 稳定编号写进原生 frame/section/layer 标题，如 `R-F01`、`G01`、`C01`、`F02-03`。重排不改编号，新版本保存 `variant_of`，编号映射到 node ID，不靠名称猜目标。
- 首次选参考时告知：“告诉我喜欢的编号，也可以在 Figma 方案旁留 Comment；下一轮我会读取评论修改。”每轮只简短提醒。评论能力按 [comment-driven-iteration.md](comment-driven-iteration.md) 执行，不能假称后台监听。
- 普通偏好问题发出后先完成不依赖答案的工作，给用户合理回复时间（简单选择通常至少约 60 秒）；无回复时可依据需求与已选参考自主选择，说明本轮默认并记为 `provisional`。用户随时可纠正。必要输入、真实访问权限或明确要求“等我选”的节点仍需等待；缺失信息不是默认值。未回复不等于用户已批准最终稿，也不授权新的付费、发布或消息操作。
- 已有品牌色或明确黑白方向时，由 Agent 判断是否缩减或跳过色材探索，说明依据并记录；不要为了固定色板数量再加一轮确认。

## 01 / 解析需求

先读文档、链接或 brief，按 [parse.md](parse.md) 区分事实与推导。对话围绕三个方向：**核心功能意象、品牌名字意象、感受与风格**。从实际名字提出可选首字母构形；交付内容优先从需求提取，仅补问缺失项。不询问使用位置，未指定时以 iOS App 图标为工作默认，平台技术确认留到导出。

功能与名字给出具体可画的候选，而非固定词表。例如键盘产品可以探索整体键盘、一个按键、输入动作或表情化反馈；Spark 可以联想火花，但不编造品牌命名故事。专业、效率等感受与扁平、3D、手绘等视觉技法分别记录。不要继承文档平台或第三方集成的品牌色，尤其不因文档位于小红书而使用小红书红。

**产出：** 2–3 个核心意象、初步风格、交付范围及确认状态。

## 02 / 找 Reference

没有项目 Figma 链接时询问一次；已有链接直接复用。按 [reference-board.md](reference-board.md) 创建独立 Reference Section，**每个意象约 30 张有效参考**，兼顾同功能产品、相关意象和不同风格。App Store 榜单、Pinterest、Logosystem、已有 icon 库、官方来源及用户 sketch 都可进入研究，明确区分真实 App、品牌标志、概念稿和用户草图。

分批导入、去重、看图核验，保留来源与可借鉴元素。用户为每类挑选 **2–3 张**，用编号或 Comment 说明偏好。实际不足时报告缺口，不拿重复图片凑数；可继续有依据的探索，但不能将缺口标成已完成。

## 03 / 延展方案 1：分层初稿

从选定 reference 提炼构形原则，建立三类初稿资产：**主 icon 黑白几何、背景、中景（适用时）**。表情适用时从主体中继续拆开。资产放各自可见 Section，参考 [modular-design.md](modular-design.md)。

先画 **6–12 个差异明显的方向**，并用 **2–3 个代表组合**检查主体、中景与背景是否成立。用户保留 2–3 个方向；已有选择直接沿用。黑白构形比较优先，不把换色算成新的形体方向。

## 04 / 延展方案 2：确认几何

合并询问初稿选择与“是否需要补充形态参考”，避免额外一轮问卷。需要时针对轮廓、结构或真实物件找图；不需要则直接细化。

**每个入选意象约 25 个几何变体**，按轮廓、比例、表情、中景样式等维度分组，统一颜色和材质。适用时比较圆形/方形气泡、不同键盘结构和表情，但题材始终由当前产品决定。用户以编号或 Comment 选形体。

## 05 / 延展方案 3：颜色与材质

几何满意后，按 [palette-board.md](palette-board.md) 建立两类对照：**色彩与材质 Section：每个选中形体约 25 个变体；背景 Section：背景颜色与材质变体**。背景数量按有意义的差异决定，不强制三种。保留独立 Palette 角色色记录，不先要求用户选择固定十组色板。

固定几何比较颜色；固定配色比较材质；背景另行对照，不做所有选项的笛卡尔积。已有充分明确的配色可缩减该阶段。用户挑选色材与背景的组合；不满意时针对反馈补参考后再生成。

## 06 / 终选方案 1

读取上一轮完整评论及回复，将选中的形体、中景、表情、色材与背景组合并修改，放到新 Section **「终选方案1」**。保留历史来源，展示实物后集中请求本轮选择或 Comment，不把参数说明塞满画布。

## 07 / 终选方案 2

根据评论针对每个待探索 icon 生成 **约 25 个变体**，允许用此前资产自由混搭，生成 **「终选方案2」**。每组仍锁定无关属性，差异须有来源与目的；用户只要求改一个角度或颜色时完成该局部修改，不机械扩成 25 张。用户继续挑选与评论。

## 08 / 终选方案 3 与 Mock

根据评论修改为 **「终选方案3」**。具体结构不确定时定向找 reference，例如修改 ISO Enter 时先看真实按键形体与透视。按 [review.md](review.md) 校验几何、遮挡、光学居中、对比与小尺寸；未通过回到对应修改，不用模糊或阴影掩盖结构问题。

把本轮入选候选同步到设备 mock，iOS 默认 iPhone。在少量清晰系统图标之后放入新方案，App 名统一使用需求中的产品名。系统图标优先可靠清晰矢量或合适分辨率资源，不能把低清截图当 SVG。手机数量、排列和壁纸沿用用户要求；建立源图标到 mock 槽位的映射。已有 mock 同步范围从首次确立起，每轮修订都同步，不必等到此步。

## 09 / 终选方案 4+ 与定稿

未满意时重复：**读取新增评论 → 定向参考（需要时）→ 修改／混搭 → 验证 → 更新 mock → 用户选择**。新轮次递增命名，不无变化地自动生成终选 4、5、6。每轮有明确反馈截止点，未回复时至多完成当前暂选版本及验证，不无限自行制造“新反馈”。任何终选轮获得明确最终选择并通过验证，均可直接交付。

停止条件是用户明确指定 final，且该源稿与 mock 已验证一致；Agent 推荐、暂选、用户批准分别记录。读不到评论、存在冲突或同步失败时保留进度，指出受影响分支，继续独立可做的工作。

## 10 / 导出

复用已有交付信息，仅在未确认时问 iOS / Android、是否打包到桌面。按当前目标平台的官方规范导出，iOS 读取 [ios.md](ios.md)。验证 SVG、PNG、比例、透明度及目标尺寸，平台蒙版与 mock 外壳不烘焙到独立图标母版中；页面截图导出单独按用户要求处理。交付真实文件路径、Figma 节点及导出清单。

只有导出成功后才说：“恭喜你拥有了一个 {品牌名} 的 logo！✨”有未完成项时如实说明，不提前宣布完成。

## 11 / 模版库

把已确认 final 的可编辑几何、角色拆分、色材参数、锚点、预览、适用约束和来源版本纳入**项目内或用户指定的私有模版库**。复用候选要有实际资产和可预览内容，不只写一句“已入库”。客户图形、评论、文档、Figma 链接不自动进入通用 skill 或公开 GitHub；跨项目复用/公开发布按用户指定范围执行。通用设计经验可以提炼成不含客户身份的规则。

## 状态与流程图

复用 `project.json` / 现有台账，记录 `workflow_version: "1.0"`、`stage`、`round`、`selected_ids`、`selection_status`、`locked_properties`、`reference_ids`、`comment_cutoff`、`source_revision`、`mock_sync_status`、`export_status`、`library_entry`。状态流按事实推进，不把工具成功当成视觉验收，也不把暂选改成批准。

如果用户要求画流程图：用一张大图或可拆阶段分区，只写关键词；用分支表达并行探索，汇合表达组合，选择节点表达收敛，虚线表达补参考与修改回路。删除旁边的长解释卡片。流程图是工作流视图，不声称已经部署可运行的图执行引擎。
